## 지금 상태 한눈에 (2026-08-05 기준 · 9회차까지 반영)

### 🔴 지금 막혀 있는 것 (5회차에서 확인)

1. **`back/.env`의 OpenAI 키가 OpenAI에서 거부된다** — 앱을 거치지 않고 `api.openai.com/v1/models`에
   직접 요청해 **401 `invalid_api_key`**. 형식·길이는 정상이므로 폐기됐거나 다른 계정의 키다.
   **유효한 키로 교체해야** AI 판단도 RAG 임베딩도 살아난다.
2. **`.env`를 고쳐도 서버는 안 읽는다** — `settings`는 프로세스 기동 시 1회만 만들어지고
   uvicorn 리로더는 `*.py`만 감시한다. **반드시 `back/`에서 재시작**(`env_file=".env"`는 CWD 기준).
3. **yfinance가 429(Rate limited)** 상태였다 — 상류 문제라 코드로 못 고친다. 시간이 지나면 풀린다.

### AI 토큰을 쓰는 곳 — 여기만 돈이 나간다

**앱 전체에서 LLM SDK를 import하는 파일은 [`llm.py`](../back/app/integrations/llm.py) 하나뿐이다.**
의도적인 설계이고, 그래서 프로바이더 교체가 파일 하나로 끝난다.

```
llm.py  ask_structured → agents/analysts.py   에이전트 3인 (병렬, 5회차부터 구조화)
                       → agents/decision.py   최종 판단 1회
        embed_texts   → services/rag_service.py  색인·검색 (5회차 신설)
                              ↓
        services/advice_service.py    일괄 응답
        services/advice_stream.py     SSE 4단계
                              ↓
        POST /api/v1/stocks/advice
        POST /api/v1/stocks/advice/stream
```

**종목 1개 분석 = LLM 4회 + 임베딩 1~N회** (AI 저널리스트 · AI 경제학자 · AI 애널리스트 병렬 +
AI 의사결정자, 여기에 새 뉴스가 있을 때만 임베딩이 추가된다 — 이미 색인된 기사는 건너뛴다).

| 토큰을 쓰는 것 | 토큰을 안 쓰는 것 (전부 yfinance·KRX) |
|---|---|
| `POST /stocks/advice` | `/markets/overview` · `/markets/movers` |
| `POST /stocks/advice/stream` | `/stocks/history` · `/stocks/content` · `/stocks/fundamentals` |
| RAG 임베딩 (색인 시 새 문서만 · 검색 시 질의 1회) | `/stocks/suggestions` · `/stocks/listed-companies` · `/health` |

프런트 진입점: [`api/stocks/advice/route.ts`](../front/src/app/api/stocks/advice/route.ts)(BFF) →
[`useAiAdvice`](../front/src/features/advice/hooks/useAiAdvice.ts)(1종목) ·
[`useBulkAdvice`](../front/src/features/advice/hooks/useBulkAdvice.ts)(관심종목 일괄).
아침 브리핑(`MorningBriefing`)은 목 데이터라 토큰을 쓰지 않는다.

### ✅ AI 토큰 안전장치 (7회차에서 셋 다 처리)

유료 키를 붙이면 실제 비용 위험이 되는 셋이었다. 전부 걸었다 — 자세한 근거는 7회차.

| 위험 | 지금 | 수도꼭지 |
|---|---|---|
| 일괄 분석 총량 무제한 (20종목 = 80회) | 캐시 적중분을 먼저 채우고 **남은 것만 10종목** | `MAX_BULK_SYMBOLS` |
| 새로고침마다 4회 재소모 | **2층 캐시** — TTL 안엔 뉴스 조회도 없고, 만료 뒤엔 기사 지문이 같으면 LLM 0회 | `ADVICE_CACHE_TTL_SECONDS` |
| `/stocks/advice` 무인증 공개 | **공유 비밀키 헤더**(`X-Advice-Key`). 프런트 BFF만 알고 브라우저엔 안 나간다 | `ADVICE_API_KEY` |

> **`ADVICE_API_KEY`를 비우면 인증이 꺼진다** (로컬 개발 기본값). 그 상태로 외부에
> 노출하면 예전과 똑같으므로, 꺼져 있으면 기동 로그가 매번 경고한다. 배포 전에
> `back/.env`와 `front/.env.local`에 **같은 값**을 넣어야 한다.

남은 비용 관련 미결: 사용자별 한도·과금은 로그인이 필요하므로 P2(관심종목 실데이터화)와 함께 간다.

## 1회차 — 2026-08-04 · 재무·밸류에이션 기능 추가

### 왜 했나

"주식에 관심 있는 사람들이 뭘 보는지" 조사한 결과, 개인 투자자의 관심은
**수급 · 배당 · 실적 · 밸류에이션**에 몰려 있었다. 반면 이 서비스는 "차트 + AI 코멘트"만 있고
상위 관심사 6개 중 5개가 없었다. 그중 **밸류에이션과 배당**은 이미 설치된 `yfinance` 하나로
전부 조달되므로 투입 대비 회수가 가장 좋다고 판단해 먼저 했다.

부수적으로 AI 에이전트가 기술적 지표(SMA·볼린저)만 보고 판단하는 문제도 있었다 —
"PER 176배인데 BUY"가 나올 수 있는 구조였다.

### 무엇이 생겼나

1. **`GET /api/v1/stocks/fundamentals`** — PER·PBR·EPS·BPS·ROE·시가총액·배당수익률·주당배당금·
   배당락일·다음 실적발표일 + 연간 매출/영업이익 4개년. 종목당 15분 TTL 캐시(심볼별 락).
2. **재무 탭이 실데이터로 채워짐** — 전에는 "재무 화면은 아직 설계되지 않았습니다"만 뜨던 빈 껍데기였다.
3. **우측 레일에 밸류에이션 3행 상시 노출** (`ValuationRail`) — 재무는 세 번째 탭이라 기본으로
   가려지는데, "지금 비싼가/얼마 주나"는 클릭 없이 보여야 하는 축이라 요약을 따로 뺐다.
4. **AI 판단이 밸류에이션을 봄** — `build_context`(에이전트 3인)와 `decide`(최종 판단) 양쪽에 주입.

### 반드시 기억해야 할 함정 3개 (실측으로 확인)

계획 단계에서 세운 가정 중 셋이 실제 호출로 뒤집혔다. **직관과 반대라 다음에 또 밟는다.**

## 2회차 — 2026-08-04 · LLM 프로바이더 Anthropic → OpenAI 교체

### 왜 했나

OpenAI(GPT) API 키를 확보해서 프로바이더를 옮겼다.

### 무엇이 바뀌었나

**바뀐 것은 [`llm.py`](../back/app/integrations/llm.py) 한 파일과 설정 4줄뿐이다.**
에이전트·서비스·엔드포인트 코드는 한 줄도 안 건드렸다 — `ask_text`/`ask_structured`
두 함수로 경계를 잡아둔 설계가 실제로 값을 한 번 했다.

| 항목 | 전 (Anthropic) | 후 (OpenAI) |
|---|---|---|
| SDK | `AsyncAnthropic` | `AsyncOpenAI` |
| API | Messages | **Responses** |
| 자유 서술 | `beta.messages.create` | `responses.create` |
| 구조화 출력 | `beta.messages.parse(output_format=)` | `responses.parse(text_format=)` |
| 시스템 프롬프트 | `system=` | `instructions=` |
| 토큰 상한 | `max_tokens=` | `max_output_tokens=` |
| 추론 강도 | `thinking` + `output_config.effort` | `reasoning={"effort": ...}` |
| 거절 감지 | `stop_reason == "refusal"` | 출력 블록의 `content.type == "refusal"` |
| 설정 | `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` | `OPENAI_API_KEY` / `OPENAI_MODEL` |
| 기본 모델 | `claude-opus-5` | `gpt-5.4` |

**없어진 설정**: `LLM_SERVER_SIDE_FALLBACK` — Anthropic 전용 베타(거절 시 서버 측 대체 모델
재실행)라 대응 개념이 없다. 없어도 앱은 규칙 기반으로 자체 폴백하므로 기능 손실은 없다.

**그대로인 설정**: `LLM_MAX_TOKENS` · `LLM_EFFORT` · `LLM_TIMEOUT_SECONDS` · `LLM_MAX_RETRIES`.
`llm_effort`의 값(`low`~`max`)이 OpenAI `reasoning.effort`와 그대로 맞아떨어져 운이 좋았다.

의존성에서 `anthropic`을 제거했다. `openai`는 원래 "설치만 되고 안 쓰는 의존성"이었는데
이제 실제로 쓴다.

### 새로 생긴 주의점

- **`LLM_EFFORT`는 gpt-5 계열·o 시리즈에서만 유효하다.** 비추론 모델을 `OPENAI_MODEL`에 넣으면
  `reasoning` 파라미터에서 400이 날 수 있다.
- **추론 토큰도 `LLM_MAX_TOKENS`를 함께 먹는다.** 이 값이 낮으면 본문이 빈 채로 `status=incomplete`가
  된다. 그대로 두면 상위에 "빈 응답"으로만 보여 원인을 못 찾으므로 `_guard()`에서 WARNING을 남긴다.
- **키가 없으면 클라이언트 생성 시점에 바로 예외가 난다.** Anthropic SDK는 호출 시점까지 미뤘다.
  다만 `get_client()`가 `ask_*` 안에서 지연 호출되고 에이전트 계층이 예외를 잡으므로,
  **동작은 전과 같다** — 200 응답 + `agents[*].status="fallback"` + `decision_source="fallback"`.
  (검증함)



3단계가 독립적으로 실패 원인을 좁힌다: ① 자격 증명·모델 접근 → ② `ask_text` 요청 형태 →
③ `ask_structured` 구조화 출력. 통과하면 실제 엔드포인트에서 `agents[*].status`가 전부
`"done"`인지 확인한다 — `"fallback"`이면 LLM이 아니라 규칙 기반으로 답한 것이다.

### 검증

`ruff` 통과, 테스트 97개 전부 통과. 키 없는 상태에서 3에이전트 → `fallback`,
최종 판단 → 규칙 기반으로 정상 degrade 확인 (예외가 밖으로 새지 않음).

**아직 못 한 것**: 실제 키로 네트워크 왕복을 돌려보지 않았다. `.env`에 키를 넣고
위 `verify_llm`을 한 번 돌려야 이 교체가 진짜로 끝난다.

## 5회차 — 2026-08-04 · AI 판단 실패 원인 규명 + RAG 1단계

### 5-1. "키를 넣었는데 AI가 거절된다" — 원인 두 개

Supabase 미연결이 원인일 것이라는 가설이 있었으나 **아니었다.** 실측으로 원인 둘을 분리했다.

**원인 ① 실행 중인 서버에 키가 없었다.**

BFF로 실제 스트림을 받아보니 세 에이전트 전부 `Missing credentials ... set the OPENAI_API_KEY`였다.
시각을 대보면 명확하다.

| | 시각 |
|---|---|
| 백엔드 프로세스 기동 | 21:58:45 |
| `back/.env` 마지막 수정 | **22:16:10** |

**서버가 떠 있는 상태에서 키를 추가**했고, `settings`는 import 시점 1회만 만들어지며 uvicorn
리로더는 `*.py`만 감시한다 → `.env`를 고쳐도 재시작되지 않는다. **재시작이 필요하고,
`env_file=".env"`가 CWD 기준이라 반드시 `back/`에서 띄워야 한다.**

**원인 ② 그 키 자체가 OpenAI에서 거부된다.**

앱을 거치지 않고 `.env`의 키만으로 `https://api.openai.com/v1/models`에 직접 요청 →
**401 `invalid_api_key`**. 형식은 정상(164자, `sk-proj-`, 공백·따옴표·비ASCII 없음),
OS 환경변수 충돌 없음, DNS·TCP 443 정상, 프록시 없음. 403(권한)이 아니라 401(모르는 키)이라
폐기됐거나 다른 계정/프로젝트의 키다. **재시작만으로는 안 되고 키를 갈아야 한다.**

**Supabase가 아닌 근거**: 코드 전체에 `supabase` 참조 0건, `DATABASE_URL`은 로컬 SQLite이고
정상 동작 중(검색·랭킹이 뜬다), 무엇보다 401은 DB를 거치지 않는 경로에서 났다.
AI 판단 경로는 DB를 읽지 않는다 — yfinance + OpenAI뿐이다.

**진단이 어려웠던 이유도 고쳤다.** LLM 실패는 전부 폴백으로 흡수되어 화면에는 "실패" 배지만
남고 원인 문자열은 SSE에만 실려 있었다. 5-2에서 근거·성향을 화면에 올리면서 이 사각지대도 줄었다.

### 5-2. RAG 1단계 — Supabase pgvector + 하이브리드 검색

**결정 사항** (선택지 검토 후): 벡터 스토어는 **Supabase pgvector**, 그래프 런타임은
**LangGraph**(2단계로 미룸), 이번 범위는 **1단계 RAG 기반**까지.

**왜 했나** — 에이전트가 받던 문서가 "가장 최근 뉴스 3건"이었다. 최신순은 관련성과 무관해서
지수 편입 공지나 배당 기준일 안내가 실적 악화 기사보다 앞자리를 차지한다.

```
수집(yfinance) → 청킹 → 임베딩 → pgvector 적재
                                      ↓
질의 ──┬─ 벡터 검색(의미)   ─┐
       └─ 키워드 검색(어휘) ─┴─ RRF 융합 → 상위 K → 프롬프트 + 인용
```

**새 파일**

| 파일 | 역할 |
|---|---|
| [`services/rag_service.py`](../back/app/services/rag_service.py) | 색인·검색·RRF 융합. 실패를 전부 흡수하는 경계 |
| [`repositories/document_chunk.py`](../back/app/repositories/document_chunk.py) | pgvector 원시 SQL. 멱등 `ensure_schema` + HNSW·트라이그램 인덱스 |
| [`core/vector_database.py`](../back/app/core/vector_database.py) | 주 DB와 분리된 엔진 + Supabase URI 정규화 |
| [`domain/chunking.py`](../back/app/domain/chunking.py) | 문단→문장 경계 분할 (순수 함수) |
| [`scripts/verify_rag.py`](../back/scripts/verify_rag.py) | 5단계 라이브 검증 **겸 최초 스키마 부트스트랩** |
| [`tests/test_rag.py`](../back/tests/test_rag.py) · [`test_advice_stream.py`](../back/tests/test_advice_stream.py) | 13 + 5개 |

**설계에서 지킨 것**

- **두 검색기를 함께 쓴다.** 벡터는 "실적 부진"과 "어닝 쇼크"를 묶지만 종목코드·수치에 약하고,
  트라이그램은 그 반대다. 점수 스케일이 전혀 다르므로(코사인 거리 vs 트라이그램 유사도)
  정규화해 더하지 않고 **순위만 쓰는 RRF**로 합친다 — 스케일 가정이 코드에 스며들지 않는다.
- **키워드 검색은 `word_similarity`(`<%`)를 쓴다.** 일반 `similarity()`는 짧은 질의와 긴 본문을
  통째로 비교해 항상 낮게 나온다. 한국어라 형태소 사전이 필요한 `tsquery`보다 트라이그램이 안전하다.
- **벡터 DB는 주 DB와 엔진을 분리한다.** 로컬 주 DB가 SQLite라 `vector` 확장을 못 올리고,
  같은 `Base.metadata`에 얹으면 개발용 `create_all()`이 깨진다.
- **인용을 검증한다.** 에이전트는 `cited_doc_ids`로 doc_id를 돌려주고
  [`resolve_sources()`](../back/app/agents/analysts.py)가 **실제 검색 결과에 없는 ID는 버린다.**
  모델이 `D9`를 지어내는 일이 있는데, 없는 출처가 "근거"로 뜨는 건 근거가 없는 것보다 나쁘다.

## 7회차 — 2026-08-05 · AI 토큰 안전장치 3종 (P1.5)

### 왜 지금 했나 — 순서를 바꿨다

문서상 P1.5였지만 P0(RAG 2단계)보다 **먼저** 했다. P0의 전제인 유효한 OpenAI 키가
아직 없는데, 그 키를 꽂는 순간 아래 셋이 전부 실제 비용으로 바뀌기 때문이다.

- 관심종목 20개 → '전체 AI 분석' 버튼 한 번 = **LLM 80회**
- 같은 종목 새로고침마다 4회 재소모
- `/stocks/advice` 무인증 공개

안전장치를 키보다 먼저 다는 것이 맞다. 셋 다 **토큰을 한 푼도 쓰지 않고** 개발·검증된다.

### ① 결과 캐시 — 왜 단순 TTL 이 아닌가

TTL 하나로는 두 요구가 충돌한다.

| TTL | 문제 |
|---|---|
| 짧게 (1분) | 비용이 거의 안 준다 |
| 길게 (1시간) | **악재 기사가 떠도 한 시간 동안 낡은 BUY 판단**을 보여준다. 투자 판단에서 이건 캐시가 아니라 오보다 |

그래서 시간이 아니라 **입력이 바뀌었는지**로 무효화한다. 이 판단의 입력 중 자주 바뀌는
것은 뉴스·리포트뿐이다(주가는 판단을 뒤집을 만큼 안 움직이고 재무는 분기 단위).
그 목록의 **지문**을 캐시 키에 함께 넣는다.

지문 확인에도 유예를 둔 것은 뉴스 조회가 이 경로 응답 시간의 대부분(측정치 95%)이기
때문이다. 매번 확인하면 LLM 은 아껴도 화면은 여전히 느리다.

```
요청 ─▶ ① TTL(600초) 안인가?
           예   → 캐시 반환. 네트워크 0회, LLM 0회
           아니오 ↓
        ② 뉴스를 조회해 지문 비교
           같다   → 캐시 반환 + 수명 연장(checked_at 갱신). LLM 0회
           다르다 → 다시 분석. LLM 4회
```

②에서 지문이 같으면 수명만 늘린다 — "기사가 그대로면 판단도 그대로"를 명시적으로
쓴 것이고, 덕분에 **조용한 종목은 하루 종일 LLM 을 한 번도 더 쓰지 않는다.**

클라이언트(React Query)는 그 위에 한 층 더 얹는다. `staleTime` 을 서버 TTL 과 같은
10분으로 두어 그 안에는 요청 자체가 나가지 않는다. 두 층이 아끼는 것이 다르다 —
클라이언트는 네트워크 왕복을, 서버는 LLM 4회를 아낀다.

**클라이언트는 "새 기사가 떴는지" 를 판단하지 않는다.** 그건 뉴스 목록을 쥔 서버만
알 수 있다. staleTime 이 지나면 그냥 다시 물어보고, 새 기사가 없으면 서버가 LLM 없이
즉시 같은 답을 준다.

### ② 총량 상한 — 대기가 아니라 거절

| 층 | 값 | 동작 |
|---|---|---|
| 프런트 일괄 | `MAX_BULK_SYMBOLS=10` | 캐시 적중분을 먼저 채우고 **남은 것에만** 상한 |
| 프런트 동시 | `MAX_CONCURRENT=3` (기존) | 그대로 |
| 백엔드 동시 | `ADVICE_MAX_CONCURRENT=4` | 초과 시 **429 + Retry-After** |

`asyncio.Semaphore` 를 쓰지 않았다. 세마포어의 `async with` 는 자리가 날 때까지
**기다린다** — 그러면 상한이 아니라 큐가 되고 LLM 호출 총량은 한 푼도 안 줄어든다.
늦게 나가는 것과 안 나가는 것은 비용 관점에서 완전히 다르다. `locked()` 로 보고
`acquire()` 하는 방법도 안 된다: 둘 사이에 `await` 가 있어 마지막 자리를 다른 코루틴이
채가면 거절하려던 요청이 대기로 빠진다. 정수 카운터는 검사와 증가 사이에 `await` 가
없어 asyncio 단일 스레드에서 원자적이다.

스트리밍은 슬롯을 **응답 헤더가 나가기 전에** 잡는다. 제너레이터 안에서 잡으면 거절을
알릴 때 이미 `200 text/event-stream` 이 나간 뒤라 클라이언트가 **거절인지 장애인지
구분할 수 없다.** 그리고 소비자가 중간에 끊어도(GeneratorExit) `finally` 로 반드시
반납한다 — 안 그러면 드로어를 몇 번 여닫는 것만으로 상한이 영구히 찬다.

캐시 적중분을 상한보다 **먼저** 채우는 순서도 의도다. 캐시 적중이 상한을 잡아먹으면
방금 본 종목 때문에 새 종목이 밀려나는 이상한 동작이 된다. 잘린 수는 `skipped` 로
돌려받아 화면이 밝힌다 — 20개를 골랐는데 10개만 도는 것을 말없이 하면 버그로 읽힌다.

### ③ 인증 — 로그인이 아니라 공유 비밀키

제대로 된 답은 사용자 인증이지만 그건 `auth.ts` 가 `providers: []` 인 지금 상태에서
P2(관심종목 실데이터화)를 통째로 끌고 들어온다. 반면 지금 막아야 하는 위협은 **"외부에서
남이 우리 토큰을 태우는 것"** 하나이고, 여기에는 프런트 BFF 만 아는 키로 충분하다.
이 프로젝트는 이미 "브라우저는 FastAPI 를 직접 호출하지 않는다"(CONVENTIONS)는 규칙이
있어 키를 실을 자리가 서버 한 곳으로 이미 좁혀져 있었다.

```
브라우저 ──(키 없음)──▶ Next BFF ──(X-Advice-Key)──▶ FastAPI
                          └ 키는 서버 측 env 에만 있다
```

- **토큰을 쓰는 두 경로만 잠근다.** `/markets/*` · `/stocks/history` · `/stocks/suggestions`
  는 yfinance·KRX 결과라 남이 불러도 우리 토큰이 줄지 않는다. 전부 잠그면 프런트 서버
  컴포넌트의 모든 호출에 키를 실어야 하고, **키가 닿는 표면이 넓어질수록 새어나갈 곳도
  많아진다.**
- **`==` 가 아니라 `secrets.compare_digest`.** 문자열 비교는 첫 불일치에서 빠져나와 응답
  시간에 "앞 몇 글자가 맞았는지"가 실린다. 네트워크 지터에 묻히긴 하지만 비밀을
  비교하는 자리에서 굳이 그 논쟁을 남길 이유가 없다.
- **미제출인지 오유인지 응답에 싣지 않는다.** 구분해 주면 헤더 이름을 모르는 사람에게
  그것부터 알려주는 셈이다.
- **미설정이면 열려 있다.** 그렇지 않으면 이 자물쇠가 "개발 시작 전에 먼저 풀어야 하는
  것"이 되어 결국 아무도 켜지 않는다. 대신 꺼져 있으면 기동 로그가 매번 경고한다 —
  **조용히 열려 있는 것이 가장 나쁘다.**

나중에 사용자별 한도·과금이 필요해지면 `require_advice_key` 를 세션 검사로 바꾸면 되고
엔드포인트는 손대지 않아도 된다.

### 이번에 알게 된 것

| 발견 | 내용 |
|---|---|
| **인증 테스트가 네트워크를 쳤다** | 키가 맞는 경로가 자물쇠를 통과한 뒤 실제 yfinance·LLM 까지 내려가 10개 테스트에 **18.8초**가 걸렸다. 서비스 경계를 대역으로 세워 0.33초. 자물쇠 테스트는 자물쇠만 봐야 한다 |
| **전역 캐시는 테스트를 거짓으로 통과시킨다** | 앞 테스트가 넣어 둔 판단을 뒤 테스트가 캐시에서 받아 **LLM 대역을 한 번도 안 부르고 초록**이 된다. conftest 의 autouse 리셋이 필수다 (재무 캐시가 같은 이유로 이미 있었다) |
| **비인라인 env 는 서버 번들에도 안 남는다** | `ADVICE_API_KEY` 로 카나리 값을 넣고 빌드해 `.next/static` 을 뒤졌더니 없었고 `.next/server` 에도 없었다. `NEXT_PUBLIC_` 이 아니면 빌드 타임 인라인이 아니라 **런타임 조회**라 이미지에 구워지지 않는다 |

### 설계에서 지킨 것

- **규칙 기반 폴백은 캐시하지 않는다.** 폴백은 LLM 이 죽었을 때의 임시 답이라 다시
  만드는 데 돈이 들지 않고, 캐시하면 키가 복구된 뒤에도 TTL 동안 '규칙 기반 판단'
  배지가 계속 뜬다 — **고장이 캐시에 굳는다.** 덕분에 재시도 버튼이 정상 결과에는
  무료(서버 캐시)로, 폴백에는 진짜 재실행으로 동작한다.
- **stage 0 에러를 성공으로 접지 않는다.** 스트림은 정상 종료하면서 에러만 싣고 올 수
  있는데(상류 429 등) 그걸 성공으로 처리하면 **실패가 캐시에 들어가** staleTime 내내
  재생된다.
- **지문은 정렬해서 해시한다.** 같은 기사 묶음이 순서만 바뀌어 오는 일이 있는데 그걸
  '새 기사'로 읽으면 LLM 4회가 이유 없이 나간다. 개수도 함께 넣어 기사가 **사라졌을
  때**도 지문이 바뀌게 한다.
- **캐시 적중이어도 SSE 4단계 계약을 지킨다.** 화면 코드는 캐시였는지 알 필요가 없고,
  사용자에게는 진행 바가 순식간에 끝난 것으로 보인다.
- **`StockAdviceResponse` 통째로 캐시하지 않는다.** 그 안의 `stock_data` 는 504봉이라
  종목 256개면 수십 MB다. 캐시해서 이득인 것은 **다시 만들려면 돈이 드는 것**뿐이다.

### 검증

백엔드 156개(신규 22) / 프런트 64개(신규 7) 통과, `ruff`·`tsc`·`lint`·`build` 통과.

테스트가 **응답이 아니라 LLM 대역 호출 횟수를 직접 센다** — 캐시가 조용히 무력화되는
회귀(키를 심볼 아닌 것으로 바꾸거나 지문에 순서를 섞는 변경)는 응답만 봐서는 안 보인다.

- 같은 종목 2회 요청 → LLM 4회 (8회가 아니라)
- TTL 안에서는 뉴스 조회 대역을 폭발하게 해 둬도 통과 (조회 자체를 안 한다)
- TTL 후 새 기사 → 8회 / 같은 기사 → 4회 유지
- 상한 초과 시 스트리밍 엔드포인트가 `text/event-stream` 이 아닌 **429 + Retry-After**
- 카나리 키로 빌드해 클라이언트 번들 유출 0건 확인

**아직 못 한 것**: 유효한 OpenAI 키가 없어 실제 LLM 왕복으로는 확인하지 못했다.
키가 생기면 같은 종목을 두 번 열어 백엔드 로그에 `AI 판단을 캐시에서 재생합니다` 가
찍히는지 보면 된다.

## 9회차 — 2026-08-05 · 관심종목 실데이터화 (P2 저장소)

### 범위 — 저장소 먼저, 로그인은 나중

로그인부터 붙이면 프로바이더 선정·세션·계정 화면이 앞에 붙어 저장소에 닿기까지 멀다.
그래서 **소유자를 불투명한 문자열 하나로 추상화**하고 저장소를 먼저 세웠다.

```
지금:   owner_key = "anon:9f3c…"   ← 서버가 발급한 httpOnly 쿠키
로그인: owner_key = "user:42"      ← 세션의 사용자 ID
```

`users.id` 외래키를 걸었다면 사용자 테이블이 생기기 전까지 이 테이블을 **만들 수조차
없었다.** 문자열로 두니 로그인이 붙는 날 할 일이 `transfer_owner()` 한 번(겹치지 않는
행의 `owner_key` UPDATE)으로 끝난다. 그 경로와 테스트를 지금 만들어 뒀다.

**이것은 인증이 아니라 식별이다.** 남의 키를 알면 그 목록을 볼 수 있다 — 그래서 값을
브라우저가 아니라 서버가 만들고(클라이언트가 만들면 아무 값이나 넣어 남의 목록을
조회한다), httpOnly 로 JS 가 읽지 못하게 둔다. 공개 배포 전에 로그인이 필요한 이유다.

### 저장하는 것과 보여주는 것을 나눴다

|---|---|
| `watchlist_items` (신규) | 그룹 · 순서 · 보유 · 알림 — **사용자가 정한 것** |
| `listed_companies` | 종목명 · 시장 구분 |
| yfinance `scan_movers` | 현재가 · 등락률 · 3개월 스파크 |

시세를 컬럼에 넣으면 그 순간부터 낡는다. 화면은 항상 최신을 원하므로 조회 시점에
붙인다. 시세는 홈·탐색이 쓰는 `scan_movers` 를 그대로 재사용한다 — 심볼 목록을 주면
한 번의 벌크 다운로드로 이름·시세·스파크를 다 채워 온다.

시세 TTL 캐시의 키는 **심볼 집합**이다. 소유자를 키로 잡으면 종목을 담거나 뺐을 때

저장소 계약 테스트 18개가 전부 통과하는 동안 운영 경로는 매 요청 롤백하고 있었다.
픽스처가 준 **세션 하나를 계속 쓰기 때문**이다 — 그 안에서는 `flush()` 든 `commit()`
이든 똑같이 보인다.

그래서 `test_watchlist_persistence.py` 를 따로 뒀다. 파일 DB에 **세션을 두 개 열어**
첫 세션이 쓰고 닫은 뒤 두 번째가 다시 읽는다. 커밋을 `flush` 로 되돌리면 이 파일의
3개가 빨개지고 **기존 18개는 여전히 전부 초록이다** — 그 대비가 이 파일의 존재 이유다.

### 화면

- **목록은 더 이상 로컬 state 가 아니다.** 변경 API 가 전부 목록 전체를 돌려주므로
  응답을 그대로 그린다 — 그룹 집계·알림 수·평가손익을 클라이언트가 다시 계산하지 않아
  서버와 어긋날 여지가 없다. 헤더·그룹 탭도 `initial` 이 아니라 최신 목록에서 읽는다.
- **순서만 낙관적**이다. 드래그는 손가락을 떼는 순간 결과가 보여야 한다. 실패하면
  서버가 확인해 준 마지막 목록으로 되돌리고 그 사실을 화면에 띄운다.
- 평가손익 합계는 **금액 가중**이다. 종목별 수익률을 단순 평균하면 100원짜리 1주와
  10만원짜리 100주가 같은 무게가 되어 합계가 실제 손익과 어긋난다.

### Next 16 — `middleware.ts` 가 아니라 `proxy.ts`

소유자 쿠키는 렌더보다 먼저 구워야 한다(서버 컴포넌트는 쿠키를 **읽을 수만** 있다).
그 자리가 Next 16 에서 이름이 바뀌었다 — 예전 이름으로 두면 파일이 조용히 무시되어
쿠키가 영영 안 심기고, **관심종목이 항상 비어 보이는데 오류는 없는** 상태가 된다.
빌드 출력의 `ƒ Proxy (Middleware)` 줄로 등록을 확인했다.

발급한 값은 응답뿐 아니라 **요청 헤더에도** 얹는다. 응답에만 심으면 이번 요청의
렌더는 여전히 쿠키를 못 읽어 첫 화면이 빈 목록이 된다.

### P0 — RAG 2단계 (다음 작업, LangGraph)

**시작 전 전제 두 개** (5회차에서 못 끝낸 것):

1. `back/.env`에 **유효한 OpenAI 키** — 임베딩도 같은 키를 쓴다. 넣고 `back/`에서 **재시작**
2. `back/.env`에 **`VECTOR_DATABASE_URL`**(Supabase URI) → `uv run python -m scripts.verify_rag`
   한 번이면 확장·테이블·인덱스 생성부터 검색까지 확인된다

그다음 1단계의 선형 코드를 상태 그래프로 옮긴다. 핵심은 **조건부 엣지와 루프**다 —
"검색이 부실하면 질의를 고쳐 다시 찾는다", "근거 없는 판단이면 다시 만든다"가 코드가 아니라
그래프 구조로 표현되는 것이 목적이다.

```
            route (종목 정규화·캐시)
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
   price        retrieve      fundamentals      ← 병렬 fan-out
      └─────────────┼─────────────┘
                    ▼
              grade_docs  ── 관련성 부족 ──→ rewrite_query ──┐
                    │◄──────────── 최대 2회 루프 ────────────┘
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
  저널리스트     경제학자      애널리스트         ← 각자 필요한 문서만 인용
      └─────────────┼─────────────┘
                    ▼
                 decide (구조화 출력)
                    ▼
                 verify  ── 인용 불일치 ──→ decide 재시도 1회 → 규칙 폴백
```
